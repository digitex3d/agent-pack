## [Unreleased]

### Added
- **The model of each `BUDGET` tier, per adapter: `adapters: [{ name: 'opencode', models: { cheap: '…' } }]`.** A built-in adapter takes its options in the config, by name; `models` maps the tiers (`cheap`, `moderate`, `costly`) to models of its harness — a key that is no tier fails the config. `claude-code` keeps haiku, sonnet, opus unless mapped otherwise; `opencode` writes the agent's `model:`; the others map none. A delegation to another harness runs the agent on the model its tier maps to there: the recipes' `{model}` slot (`opencode run --model <id>`, `codex exec -m <id>`), shown by the apx as `# model: …`. A tier the harness maps to none is a build warning, and runs on the harness's default.
- **A list of contracts on another harness: `DELEGATE <list> BY <harness>:<agent>`** *(D66)*. It compiled to a background agent of the harness running the flow, the harness dropped; it now compiles to `apx contract start <mrk-id> --by <harness>:<agent>`, which opens each copy, carries the agent's definition in, writes the prompt (spec, zones, marks) and prints the harness's command, filled, for the lead to run; `apx delegate deliver <ctr-id> --answer` keeps the answer and the contract's zones — never what was carried in.
- **A copy links the project's dependency folders.** A copy that reads every tracked file — a contract's, a delegation's to another harness — now links the ignored `node_modules`, `vendor` and `.venv` from the working folder, so the project's own checks run in it.
- **An agent may bind several roles: `AS reviewer, explorer`** *(D17)*. A role is a craft many agents share; each one an agent binds adds its identity line (in the order written), its rules and its imports — a rule two roles share is kept once, and two roles that disagree on a rule (`ALWAYS x` / `NEVER x`) fail the build. `AS` is optional: an agent may bind no role. Any number of agents may bind the same role: the index no longer fails with "ambiguous role binding"; a `BY <role>` that several members hold fails where it is written, asking for the agent's name. Not breaking: `AS <role>` with one role compiles exactly as before.
- **Delegating to another harness: `BY <harness>:<agent>`** *(D66)*. A `DELEGATE` hands its task to an agent of the project as another harness runs it, launched from outside as that harness's adapter describes in its recipe (`invoke.ap`, a TEMPLATE whose BODY is the command line; `invocation` on the adapter). The harness is a dependency of the build — enabled in `adapters:`, with a recipe, its CLI on the PATH — or the compilation fails, saying which. The piece works in a copy of its own: `apx delegate start` opens it, carries the agent's definition in, writes the prompt (the task and the variables it reads, or the form of its `AS`) and prints the command filled; `apx delegate deliver <dlg-id> --answer` keeps the answer and, of what the copy changed, only what stays within the perimeter; a WAIT merges it. `FORK … BY <harness>:<agent>` is an error. New command: `agent-pack harness list` — installed, enabled, delegable, CLI on the PATH.
- **The `codex` adapter.** Agents as Codex custom agents (`.codex/agents/<name>.toml`: `name`, `description`, `developer_instructions`), skills as `.agents/skills/<name>/SKILL.md`; Codex reads `AGENTS.md` itself. Its recipe runs `codex exec` in the delegation's copy, the answer written with `-o` and bound with `--output-schema` under an `AS`. `claude-code` ships its recipe too: `claude -p --agent <agent>`.
- **The perimeter is kept before every write** *(D65)*. A piece started in the background records its perimeter (`delegate start`): the `WRITES` globs of its step's `@WITHIN` and of its assignee's own — `take` and `reassign` set it again. `apx guard <path> [--agent <name>] [--subagent] [--after]` says whether a write keeps to the work in progress: the main conversation is held to none; a subagent named as a piece's assignee to its pieces; one no piece names (a fork, an agent no flow started) to every piece in progress with a perimeter; every agent to its own `@WITHIN`; a contract's assignee writes only in its copy. The `claude-code` adapter installs one hook of the project in `.claude/settings.json` (`PreToolUse` and `PostToolUse` on `Write|Edit|MultiEdit|NotebookEdit`, script `.agent-pack/hooks/claude-code-guard.mjs`), which runs inside subagents too and reads `agent_id` / `agent_type`: a write outside is denied, and so is one the check could not decide; after a write in a contract's copy it warns as before. Only agent-pack's entries are written, and removed when no agent works under a perimeter. An adapter may keep project settings with `projectSettings`.

- **The Claude Code adapter has its own words for background work, forks and waits.** An adapter may now word a flow's delegation lines over the neutral ones — `renderings.DELEGATE.background`, `renderings.FORK.self` / `.agent` (`{definition}`: the command that reads the agent's definition), `renderings.WAIT.run` — carried in `meta.phrases` to every place a flow is rendered. `claude-code` says: a `~` is a background agent (the Agent tool, `run_in_background: true`); a `WAIT` never blocks the session — the lead goes on only once the notification of each piece has come, records one that ended without delivering (`delegate ended`), then reads the states with `apx wait … --now`; a `FORK` is a native fork (`subagent_type: "fork"`), and `FORK … BY y` one that first reads who `y` is (`y.apx scope`) and follows `y`'s rules. Every other adapter keeps the neutral words: `apx wait` blocks until each piece is settled or the limit. In the code: `delegationPhrases` and the phrase merge in `src/delegation.ts`, `MdEnv.phrases`.
- **`apx wait … --now`.** No waiting: each piece's state at once, its limit counted from when it started — `running, within its <max>` or `still running after <max>`, the lead's to decide.
- **The apx tracks what a flow starts in the background: `delegate start|deliver|block` and `wait`.** Each `DELEGATE~` / `FORK~` of a flow gets an id (`dlg-…`, `meta.background`) and, once started, a record in the session's registry (`.agent-pack/state/<session>/delegations.tbl`) — on disk, it outlives the conversation. The compiled flow names the commands on each line: `<apx> delegate start <dlg-id>` before the lead hands the piece over, `delegate deliver <dlg-id> -` (the result on stdin, stored in its `INTO` variable and checked against its type — exit `6` and nothing stored when it breaks it) or `delegate block <dlg-id> "<why>"` from whoever carries it out, and at each `WAIT` the ids it takes back: `<apx> wait <dlg-id> … [--max <duration>]` (also `wait <var>`, `wait all`). The wait returns when each piece is delivered, blocked or ended without delivery, or at its limit — `WAIT … MAX <duration>` in the source (`90s`, `10m`, `2h`; anything else fails the build), else the new `wait: { max: '30m' }` config key; then each one's state, exit `0` only when all were delivered. Nothing is settled by itself: at the limit what still runs is left running, and the lead decides — wait again, `delegate take <dlg-id>`, `delegate reassign <dlg-id> <agent>` or `delegate block`; `delegate ended <dlg-id>` records a piece whose agent stopped without delivering, `delegate list` shows them all. In the code: `src/apx/delegations.ts` (the registry), `src/apx/recordTable.ts` (one table implementation for it and the contracts' instances), `bindBackgroundWork` and `parseWait`/`parseDuration` in `src/delegation.ts`, `waitFor` in `src/apx/services/delegate.ts`.
- **`FORK … AS <template>`.** A fork still inherits the conversation; an `AS` (`AS!`, `AS!!`) shapes what it is handed on top of it, and its compiled line says so. The error for `FORK … AS` is gone.

- **Plugins: a block and the apx commands that serve it.** A plugin is a folder named in the config (`plugins: ['./plugins/checklist']`): `plugin.ap`, its manifest, and `service.mjs`, one function per operation. The manifest is written in the language: `PLUGIN <name>:` with `ABOUT`, `AS <template>` (the record its block's lines are — slot `item` is the line `ITEM`, repeated for a `LIST` slot) and `OPERATION <op>:` blocks, each with `ABOUT` and an optional `AS <template>` for its input. One name gives the rest: plugin `checklist` declares the block `CHECKLIST` (inline in an agent, or a `checklists/` library file), ids `che-…`, and the commands `<apx> checklist <op> <che-id> field=value …` (or `-`, JSON on stdin). `bundle` refuses a broken manifest, a template it names but does not declare, an operation without its function (or a function no operation declares), and a name, prefix or folder some kind already has; a block's lines are checked against its template, in the block's own words. The apx checks the operation, the id and the input against the manifest before it calls the plugin's function with `{ block, input, state, out }`; `state` is the block's memory in the session, written only when the function returns. A template may now name a scalar template (`item: <check>`, `LIST <check>`): its values are checked against the scalar's type. A plugin to read and copy ships in `templates/examples/plugin-example/`: `checklist`, with an agent that uses it inline and from the library, and a README on how a plugin is made; the plugin tests run it as it ships. `PLUGIN` and `OPERATION` are blocks of the language, checked by their contracts like every block. In the code: `src/plugins.ts` (the spec, read alike by compiler and apx), `src/pluginLoader.ts` (read, check, install into the tables the core already has), `PluginBlock`, `src/apx/services/plugin.ts`.

- **A domain formula is decided by the judge of the lines.** `WRITES! <formula> [IN <glob>, …]` and `READS!`/`!!` now compile when the config has a `judge`: at compile time the judge answers, for each file of the formula's `IN` (or of the whole project, the judge lock aside), from its path and its text, the probability that it belongs. The new `domains: { in: 0.8, out: 0.2 }` config key splits them: at or above `in` within, at or below `out` outside; between them, under `!`, the agent decides — the scope warning and `apx scope` list those files with their probability, and `contract within` adds a word when one is written in a copy — while under `!!` they stay outside. The probabilities travel with the `DOMAIN` block into the apx; the verdicts go into the domain file's unit like the judge's others, keyed by the question and the file's path and text — a rebuild asks only about new or changed files, and about all of them when the formula changes; a decision in the judge lock wins. Without a `judge` a formula still fails the build, now with the key to add; a formula that places no file fails like a domain whose globs match none; a file the judge could not answer for stays outside, with a warning (an error with `judge.offline: 'error'`). In the code: `src/judge/domains.ts`, `JudgeRun.fileVerdict` (one ask path with the lines' checks), `questionKey`, `DomainBlock.formulas` / `side()`, `literalGlob`.

### Removed
- **The `junie` adapter** — gone from the built-in adapters, with its files; a config that names it fails with the list of the built-in ones.

### Changed
- **The contracts' hook moved from the agents' frontmatter to the project's settings** *(breaking for hand-written frontmatter that relied on it)*. `claude-code-within.mjs` is gone: `claude-code-guard.mjs after` gives the same warning.
- **`EACH` is a block of a flow step; `PARALLEL EACH` is gone** *(breaking)*. `EACH <item> IN {{<list>}} MAX <n>:` holds `DELEGATE` and `FORK` lines only and runs each once per element of the list, all the runs at once: without `~` the flow waits for every run where the `EACH` stands, with `~` the step's `WAIT` takes them back. The list is read like any variable, and is a variable typed with a template of one `LIST` slot; `MAX` is required, and a list longer than it stops the flow (`delegate start` refuses the run past it, exit `3`). Inside an `EACH`, each run of a `~` is a piece of its own, `dlg-…-<k>`; its result stays with the run, and once every run is settled the `WAIT` stores one result per run, in order, into the delegation's `INTO` — a plain variable (a run not delivered as its state), or one typed with a template of one `LIST` slot (only when all delivered); anything else fails the build. A run that fails does not stop the others. An `EACH` over a list a `MARK` filled fails the build: a list of contracts is delegated as it is. `PARALLEL` — bare or `PARALLEL EACH` — fails with the rewrite. In the code: `parseEachHead` / `eachHeadOf` (`src/vars.ts`), `EachNode` (`type: 'each'`) in place of `ParallelNode`, the `EACH IN` block contract, the EACH binding in `bindBackgroundWork`, `pieceOf` / `runsOf` and the run collection in the delegate service.
- **After its `WAIT`, a list of contracts reads each one's state.** `{{<list>}}` held the contracts' ids; once the `WAIT` takes them back it holds each one's id, state (`merged`, `blocked` with its reason, `ended without delivery`) — what `IF {{screens}} has a blocked screen:` judges.
- **Contracts are promises a flow makes: `MARK`, then `DELEGATE <list>`** *(breaking for teams of contracts)*. In a flow step, `MARK <criterion> INTO <list> AS <spec> [MAX <n>] [WITHIN <domain>]` has whoever runs the flow pick zones of the code and bind each to a contract that waits: `<apx> contract mark <mrk-id> -` checks its spec against the template (exit `6`), refuses past `MAX` or the new `mark: { max: 20 }` config key (exit `3`), and adds the contract's id to the list — a variable declared like any other; the marks, `agent-pack <ctr-id>` … `agent-pack end <ctr-id>` in comments, stay in the code. `DELEGATE[~] <list> BY <agent>` starts every contract waiting in it, one each, all at once, all to that one agent (`<apx> contract start <mrk-id> --by <agent>`: zones found by their marks, a copy each); without `~` it waits for them where it stands, with `~` at its `WAIT` — `<apx> wait <mrk-id>` merges each delivery and lands it in the working folder, uncommitted (`contract merge <ctr-id> --prefer ours|theirs`, then `contract land`, after a conflict). A contract writes its zones, the files it creates and its `MARK`'s `WITHIN` domain — which must stay inside the work's perimeter — and its delivery (`delegate deliver <ctr-id>`, `--why` for what it leaves out) keeps just that; `delegate block|ended|take|reassign|list` work on it as on any piece. Contracts live in the one registry, `delegations.tbl`, beside the background pieces; `contracts.tbl` is gone. Gone too, each failing with the rewrite to `MARK` + `DELEGATE`: `STRATEGY contracts`, `LEAD`, the `CONTRACT` blocks of teams and of the project file, a contract's `DOMAIN` and `WITHIN zone|file|domain`, the instance a team was handed (`WHEN handed <contract>:` is a plain trigger again), `depends`/`parent`, the generated flow and its prose, `contract new|dispatch|deliver|take|block`. The `PostToolUse` hook now goes to the agents of a team whose flows `MARK`. A `DELEGATE` of a variable no `MARK` above it filled fails the build; a `DELEGATE` of a list takes no `AS`, no `INTO` and no lines beneath it. In the code: `parseMark` / `markLineErrors` / `ApMark` and the MARK binding in `src/delegation.ts`, `meta.marks`, `DirectiveNode.mark`/`list`/`max`/`within`, the contract steps in `src/apx/engine.ts` behind `host.contracts`, `DelegationTable.batchOf`, `Allowed.created` in the workspace; `ContractBlock`, `ContractTable`, `ContractIndex` and `src/services/contractsFlow.ts` are removed — a flow's `BY <team>` resolves against the project's team names (`teamNamesUnder`).
- **A team's flows are checked line by line.** A `STEP` in a team file's `FLOW` holding a `BY` line (or any line a step does not hold) now fails the build with its rewrite — the compiler and the orchestration ran only the team block's own check, so `STEP … BY builder` compiled as before. A bare `PARALLEL:` is told its rewrite to `DELEGATE~` + `WAIT ALL` instead of "needs its text on the same line"; so are `STRATEGY` and `LEAD` written alone.
- **The `ask` service is `delegate`** *(breaking)*. `<apx> delegate input <exe-id>`, `<apx> delegate answer <exe-id> -` — the compiled lines name them; `<apx> ask …` fails with the new name. The same service serves the background pieces of a flow (see *The apx tracks what a flow starts in the background*).
- **One way to hand work over: `DELEGATE`, `FORK`, `~` and `WAIT`; a step is a label** *(breaking)*. A flow's `STEP <title>:` names no one: it groups the lines whoever runs the flow carries out. Work goes to someone else by a delegation — `DELEGATE <task> [INTO <name>] BY <agent or team> [AS <template>]`, a line or a block whose `DO`, `RUN`, rules and `IF`/`ELSE` are what that agent is told — and its form says the context: without `AS` all of it, with `AS <template>` (at any level) only what the template holds; `FORK <task> [INTO <name>] [BY <agent>]` hands over the conversation itself, a fork of whoever runs the flow or that agent on it. `DELEGATE~` and `FORK~` start the work and go on; `WAIT <name>, …` / `WAIT ALL` takes it back, every piece delivered or blocked. What a `~` starts is waited for before its step, branch or loop ends, and read only after its `WAIT` — each of these fails the build with its line; `~`, `WAIT` and `FORK` stand only in a flow step. `DELEGATE` replaces `ASK` in an agent's body too, with its contract as before (`AS` there is the shape of the delegate's input). Gone, each failing with its rewrite: `ASK`, a step's `BY`, `CONTEXT` and `AS` lines, the `CONTEXT` modes, and the bare `PARALLEL` (`PARALLEL EACH` stays). A checked condition in a flow is the one of the agent its `DELEGATE … BY <agent>:` block goes to. The flow of a team of contracts is generated in the new form (its workers now get all the context). The Claude Code Workflow script runs each `DELEGATE` as its agent, starts a `DELEGATE~` and awaits it at its `WAIT`, and binds a delegation's `AS` as the schema of the answer before it; a flow with lines of its own for whoever runs it stays prose. In the code: `src/delegation.ts` (the reading of a delegation line, its rendering, the structured-concurrency check), `DirectiveNode.as` / `async`, `StepNode` without `by`, `context` and `shape`, the `DELEGATE` block contract, `REMOVED_KEYWORDS` in the lint.
- **Domains say their files with `WRITES` and `READS`, and `@WITHIN` puts work within them** *(breaking)*. A `DOMAIN` holds `ABOUT`, its tags on `APPLIES` (tags only — a perimeter fails), and lines that add up: `WRITES IN <glob>, …`, the files work within it may write, and `READS IN <glob>, …`, those it may only read; `FOR` gives way to them and fails with the rewrite. A domain whose globs match no file of the project fails the build. A line may describe its files in words — `WRITES! <formula> [IN …]`, `READS!! …` — for a judge to decide file by file, its `!`s weighing the judgement as `IF!`'s; a formula without `!` fails (see *A domain formula is decided by the judge of the lines*). The agent's `WRITES <domain>` and `READS <domain>` lines are gone (they fail with the rewrite): the second decorator, `@WITHIN <domain>, …` (or `@WITHIN #tag`), right above an `AGENT`, puts all its work within those domains — the perimeter (`doc.perimeter()`, the scope warning, `apx scope`, the copies and deliveries of a team of contracts, a `CONTRACT`'s `DOMAIN` check) is their `WRITES` globs, and their `READS` ones (none: whatever it needs). `@WITHIN` stands only right above an `AGENT`, a `TEAM`, a `FLOW` or a `STEP` — anywhere else, or opening a block, it fails the build; nested, it names only domains of the enclosing one — never a silent intersection — and a step's names only domains of its `BY` agent's, when a `@WITHIN` decorates that agent. In the code: `src/domains.ts` (the one reading of a domain line), `WITHIN_DECORATOR` with an `on` list in the registry (the blocks a decorator may stand above, checked by the parser for any decorator that has one), `DecoratorScope.outside`, `doc.domains()` / `doc.definitionUses()`.
- **A decorator stands above any block — a definition too.** Above an `AGENT`, a `PROCEDURE`, a `TEAM`, a `FLOW`, a decorator decorates all the work of the definition (its body, walked inside the decorator); above a `TEAM`, every flow of the team; it decorates only what is written beneath it — an agent a decorated team calls keeps its own. A decorator above a definition with no work (a `TEMPLATE`, a `DOMAIN`) fails the build, and a definition inside a decorator's block still does — it is decorated from above. The error for a decorator above a definition is gone.
- **`WITH` is a decorator: `@WITH`** *(breaking)*. A decorator says under which conditions the work it decorates is done: `@WITH pdf` right above a `WHEN`, an `IF` or an `UNTIL` decorates that block; `@WITH pdf:` in a body decorates the lines nested beneath it. Names, tags (`#policy:<tag>`, `#skill:<tag>`), harness skill names (`plugin:skill`) and `@WITH <skill> AS <template>` read as before; several decorators stack, one per line. A decorator that decorates nothing — above a line, at the end of a body, opening a block with nothing nested — fails the build, and so does one above a definition (a definition is decorated from inside its body: `@WITH x:` first in it) or a definition inside a decorator's block. `!WITH` is removed: a policy says where it holds with its `APPLIES` line. An old `WITH x:` or `!WITH` line fails the build with the rewrite. In the code, decorators are one family (`src/decorators.ts`): a registry with one entry per decorator — the kinds its items name, how nested ones combine (union or intersection), the opening of its sentence — and one way, for all of them, to lex, attach, lint, resolve names and tags, build the document's node, carry the scope down a walk and render (`src/decoratorUse.ts`, shared by the document builder and the standalone renderer). `@WITH` is its first entry; the `WITH` force family, `isWithHead` and the WITH-only code of `withUse.ts` are gone.
- **One form for every kind the apx serves** *(breaking)*. A store, a dimension and a delegation are served by one service each, reached by the kind's name in one form: `<apx> <kind> <operation> [<id>] …` — `store a <sto-id> topic=…`, `dimension read <dim-id> <file>`, `ask input <exe-id>`, `ask answer <exe-id> -`. A store is no longer reached by its name (so a store may now be named like a verb; the check is gone), a dimension's id follows the operation, and `input`/`answer` are the operations of `ask` (`run`, a program's, stays the engine's). `help` lists every service's operations. In the code, one `ApxService` per kind (`src/apx/service.ts`, `src/apx/services/`), registered once and read by the engine's dispatch, the help and the compiled definition; the engine keeps only what is its own.
- **`OWNS` is replaced by domains** *(breaking)*. A region of the code is a block of its own — `EXPORT DOMAIN api:` with `ABOUT` and `FOR src/api/**, …` (the dimension's line), in the library's `domains/` (`IMPORT api FROM @main.domains`) or at the top of the agent's file — and an agent names the domains it may write, `WRITES api, db`, and the ones it may only read, `READS content`. The compiled definition opens with the scope warning listing their files (`Read whatever you need.` without `READS`) and lists the domains in a *Domains* chapter; `apx scope` prints the perimeter. A name that is no domain, a domain listed twice, or one both written and read fails the build. `OWNS` fails with the rewrite. `doc.owns()` is `doc.perimeter()` (`{ writes, reads }`, as globs).
- **A contract's domain is a DOMAIN block, no more the judge's guess** *(breaking)*. The team's `DOMAINS <dimension>` line is gone — it fails with the rewrite — and so is tagging every file with its domain by a judge's choice question (`src/judge/domains.ts`, the domain cache, the terminal prompt on a grey file). A `CONTRACT`'s `DOMAIN api` goes to an agent that writes it: a `BY` agent without `WRITES api` fails the build. The lead's `contract dispatch` looks for the zones in the files it writes (its `WRITES`), and no longer asks the judge whose a file is. The `margin` keys of `judge` and `checks` are removed (an error naming why), choice questions leave the judge interface and the Jev adapter, and a domain a developer once chose in the judge lock is dropped at its next write.
- **The instances of a contract work in copies of their own** *(breaking for teams of contracts)*. `contract dispatch` opens a copy per instance (`.agent-pack/work/<ctr-id>`) from the working folder as it is — uncommitted changes included — showing what its assignee reads and writes; the assignee works there with any tool, and `deliver` keeps what its contract admits, so what an instance wrote is its copy's diff, never a guess. A contract says how far: `WITHIN zone` (the lines between its marks), `WITHIN file` (the files holding its zones) or `WITHIN domain` (its assignee's `WRITES`, the default). Zones are optional — new code needs none — and an instance may have several, in several files; the lead's marks stay in the copy and the delivery drops them. Anything outside the limit is left out of the delivery, and only with a reason (`deliver <ctr-id> --why "…"`). `contract within <ctr-id> <path>` tells whether a file stays within, and Claude Code asks it after every Write or Edit in a copy: a `PostToolUse` hook in the frontmatter of the agents of a team of contracts only, whose script (`.agent-pack/hooks/claude-code-within.mjs`) hands the warning back as context and never touches the write — a write through Bash meets the same check at deliver. The lead merges each delivery as it comes (`merge <ctr-id> [--prefer ours|theirs]` on a conflict), sees what was left out and why, takes a blocked instance over in its copy (`contract take`), and delivering the request lands the work in the working folder, uncommitted — so does each new `dispatch`, before its copies open. Gone: the perimeter fingerprints (`skeleton.json`), the freeze while work runs, a zone being one file and a file one assignee's. The project must be a git repository (git 2.38 or later): the copies are git worktrees and hidden refs (`refs/agent-pack/<session>/`), never a branch or a commit of the developer's; `adapters/git` behind a workspace interface (`src/workspace`), the first of its registry.
- **Every list is comma-separated** *(breaking)*. One form for the whole language: `FOR src/api/**, src/db/**`, `EXPERTISE code-review, refactoring`, `APPLIES #board, universal` and `ENUM[low, high]` now separate their items with commas, as `IMPORT`, `MEMBER`, `BY` and `WITH` already did. A comma inside `{…}` belongs to a glob. The old space-separated form fails the build with the line to write (`` `FOR a b`: separate the items with commas — `FOR a, b` ``). One reader, `splitList` (`src/lists.ts`), replaces the fourteen places that split a list each on its own. The `APPLIES` lines agent-pack writes itself are comma-separated too.

### Added
- **`dist/keywords.json` — every word of the language, with its role.** The build writes it from the compiler's own registries (`src/keywordCatalog.ts`): `block` (`AGENT`, `ROLE`, `EXPORT` …), `rule` (a rule family's force level and its aliases — `MUST`, `NEVER`), `meta` (an agent's descriptive fields — `ABOUT`, `BUDGET`), `keyword` (every other word). The tools that show `.ap` sources read it instead of keeping a list of their own: the IDE plugin colours by it.
- **A flow step may be handed to a team.** `BY <team>` in a step names another team of the project: the step is handed to it as to one agent — it runs the flow its routing picks (a team of contracts: its contracts flow), with the step's input and context, and that flow's result is the step's answer. AGENTS.md says so in the Flows chapter. A flow with such a step is run from its text, never compiled into a Workflow script.
- **`BUDGET` is back — an agent's cost tier.** `BUDGET cheap | moderate | costly` in an `AGENT` block; the adapter maps it to a model of its harness (`claude-code`: haiku, sonnet, opus — the agent's `model:`). It wins over the config's `delegate.models`; without it, the config decides as before. The source names a tier, never a model.
- **`EXPORT VAR` — variables are exported and imported like every other block.** Any module of a library declares a variable on one top-level line: `EXPORT VAR board = Product` (a constant), `EXPORT VAR draft` (private: each agent that imports it has its own), `EXPORT SESSION VAR plan AS implementation-plan` (shared by the session's agents that import it). An agent, a team's `flows.ap` or a library module takes it with `IMPORT plan FROM @main.vars` — the same resolver as templates: the block's name is matched, not the file's. A module only declares: `EXPORT VAR x:` is an error, and so is an indented `EXPORT VAR`.
- **`SKILL` — a skill is an agent the adapter writes as a skill.** `EXPORT SKILL <name> AS <role>:` takes every line an `AGENT` takes and compiles the same way, with its own apx; it lives in the project library (`skills/`) and `bundle all` builds every one. `claude-code` writes `.claude/skills/<name>/SKILL.md` (the compiled definition), `claude-code-apx` the same file pointing at the skill's apx, `codex` `.agents/skills/<name>/SKILL.md`, `cursor` a `.mdc` rule applied on its description. The frontmatter is its name and its `ABOUT`. A skill declares, assigns and reads variables like an agent.
- **An agent imports skills.** `IMPORT pdf-report FROM @main.skills` brings a library skill; `IMPORT pdf FROM @harness.skills` names a skill the harness provides itself — never compiled or written, the name as the harness knows it (`anthropic-skills:pdf`). Imported skills fill the *Skills* chapter: the agent may use each whenever it judges it fits, and its entry says how to load it — run the skill's apx, or ask the harness (Claude Code: the Skill tool). An adapter words it with `renderings.SKILL.apx` / `renderings.SKILL.harness`. A skill's body stays in its apx. A skill from a shared library is refused: only the project's library is built.
- **`WITH …:` — a block that says which work skills, policies and dimensions are for.** The lines nested below it are under the skills and policies it names, and read the dimensions it names — by name, or (a skill, a policy) by a tag with its kind, comma separated (`WITH developer-reasons-first, #policy:review, #skill:design:`); a tag is expanded at compile time into every imported block of that kind that carries it on its `APPLIES` line, each with its id. `WITH <skill> AS <template>:` shapes one named skill's answer; `!WITH …:` keeps the lines out of them. It stands in a body (an agent, a role, a procedure), around lines — never a block; first in a procedure's body it covers the whole procedure, which carries it when imported. `WITH` is a force-level family (`renderings.WITH` rewords it: *For the work below, use …*); a flow step and a `COMPUTE` block take none. The node lists what it names (`uses`). A name or a tag that selects nothing, a tag without its kind, a `WITH` with nothing nested below it or around a block, and an `AS` on `!WITH`, on a tag, on a policy or on more than one name fail the build.
- **A policy, and a skill, hold where their scope says.** `APPLIES universal` — everywhere imported; `team:<team>` — in that team's members; `agent:<agent>` — in that agent; otherwise only in the lines a `WITH` names them for. A policy or a skill imported where it holds nowhere fails the build — a skill of `@harness.skills`, which has no `APPLIES` line, is named by a `WITH`. A `SKILL` block takes its own `APPLIES` line, read by whoever imports it. Every policy and skill opens, in the compiled definition, with the line that says where it applies; `ls kind=policy` / `kind=skill` shows its scope. The *Policies* and *Skills* chapters say to apply each one wherever its scope line says. A dimension, which has no `APPLIES` line, holds where a `WITH` names it and nowhere else: one no `WITH` names draws a warning — *dimension `x` applies nowhere — name it in a `WITH x:` block around the lines that read it* — and is served by the apx all the same; its entry in the *Dimensions* chapter opens with that scope line, and `ls kind=dimension` labels it *only where a WITH names it*.
- **`PROJECT.ap` reads WITH like an agent.** Its `AGENTS.md` gets a *Skills* chapter for the skills it imports, and a name, a tag or an `AS` template that selects nothing fails the build at the file and line it was written in — an imported procedure's own.
- **`WHEN!` — a trigger whose condition a judge decides.** `WHEN! <condition>:` is sugar, rewritten before compilation into `WHEN <condition>:` with `IF! <condition>:` beneath and the trigger's lines under that — byte-identical to the hand-written pair, so every rule of `IF!` holds: the condition reads at least one variable, `checks` must be configured, the agent whose apx answers for it runs `check <cnd-id>`. The agent still picks the moment; the judge decides the condition and wins. `WHEN!!` fails the compilation — a sealed condition has no moment the agent could see: write `WHEN <moment>:` with `IF!! <condition>:` beneath. `!WHEN` and `WHEN*` fail too.
- **`PARALLEL EACH` — one step, run once per element of a list.** `PARALLEL EACH <item> IN <list> MAX <n>:` holds one step and runs it for every element of the list at the same time; in the step `{{<item>}}` is the run's element. The list is a variable typed with a template holding one `LIST` slot — filled by an earlier step with `DO … INTO <list>`. `MAX` is required (a whole number of at least 1); a list longer than it is an error that stops the flow. A run that fails does not stop the others: its report goes on with theirs. A step `BY` the agent that split the work, with `CONTEXT inherited`, is its clone. A missing or bad `MAX`, more than one step, or a list that is no variable, has no type or has not exactly one `LIST` slot fail the build. `claude-code` leaves such a flow to its prose: the Workflow script does not hold the list.
- **`DIMENSION` — answers about the code, worked out once and kept by the apx (D43).** `EXPORT DIMENSION pseudocode:` with `ABOUT` (the question it answers), `FOR <glob> …` (the files it covers, from the project root), `EACH` (what to translate inside a file — prose, or a template's name, rendered as its reference), `AS <template>` (its value for a file: a list of instances, or `none`; no level, a template with `SLOTS`) and rule lines on how the value is produced. Declared and imported like a store (`dimensions/`, `IMPORT … FROM @main.dimensions`) or written in the agent's file — at its top or directly in the agent's body, nowhere else. The body is strict: any other line — an action, a line of prose, a `WHEN`, a nested block (`IF`, `ON-…`, `UNTIL`), at any depth — a missing one, `AS!`, a `FOR` glob that is absolute or goes through `..`, a name that is an apx verb or a store's, fail the build wherever the block is written, and `agent-pack lint` reports the same errors. `FOR` and `EACH` are a dimension's lines only; `FOR` alone says *FOR needs at least one glob*. A dimension is an agent's: `PROJECT.ap` or a team's `flows.ap` that imports or declares one fails the build. The compiled agent gets a *Dimensions* chapter: where each applies, what it covers, how to read it and write it, its rules. When it is worth reading is the reader's to say, never the dimension's: a `WITH` names it above the lines that read it (see `WITH`), and a moment the judge decides is a `WHEN!` with the `WITH` beneath; once read, the agent decides whether it also needs the code.
- **apx: a dimension's verbs.** `dimension <dim-id> read <file> [json]` — `hit` and the answer (each instance through its template's `BODY`) while the file and every file the answer depends on are unchanged, `miss` with why (`never written`, `changed: <path>`, `ref gone: <path>`), `gone` for a deleted file; a file moved without an edit takes its entry along. `<dim> write <file> [refs=a;b] -|none` checks the file is covered and exists, the refs exist, the value fits the template (the typed-variable check), and never overwrites a fresh answer (exit 4); every project file the value names is a ref too. `<dim> ls|why|clear|gc`, and `dims` for every dimension's cache folder and counts. The cache: `.agent-pack/cache/<defhash>/<file>.json`, the defhash being the content of the dimension, its `AS` template and the template its `EACH` names, all without their names (a rename keeps the cache, an edit starts a new one); an entry of another format reads as never written; read counters in `.agent-pack/cache/stats/`. A file's fingerprint ignores line endings, trailing whitespace and blank lines; indentation and comments count. `bundle all` removes the cache folders no dimension produces any more. `dims` joins the apx verbs: no store or dimension may be named so.
- **`CONTEXT <mode> AS <template>` — a step's context and input shape on one line.** `CONTEXT summary AS! review-brief` reads exactly as `CONTEXT summary` with `AS! review-brief` beneath: the mode in the step's signature, the shape opening the step, in the compiled agent, `AGENTS.md` and `apx flow` alike. The mode is checked alone (`CONTEXT summery AS! x` is an unknown value) and so is the level of `AS`. Until now the whole rest of the line was taken for the mode and failed as an unknown value.
- **`AS` in a `WHEN` block — each trigger its own answer shape.** An `AS <template>` line written directly in a `WHEN <trigger>:` block (an `ON-…` hook, a `WHEN!` too) shapes the answer of that moment: it opens the trigger's body in the compiled text, at its force (`AS!` → *Strictly shape your response as …*), the WHEN node carries it (`shape`), and `apx` lists it beside the trigger (`— as <template>`). Until now such a line was taken as the agent's own shape and printed nowhere. It is the path that replaces `LENS-OUT`, now a candidate for deprecation.
- **One judge rule, many keywords.** A `#judge` template whose `BODY` opens with an `ENUM` slot — `{keyword} {action}` with `keyword: ENUM[DO MUST ALWAYS SHOULD MAY]` — judges the lines of each of its values, whatever their force (a `NEVER` line is an `ALWAYS` line). Each value is checked like a `BODY` word: `NEVER` must be written `ALWAYS`, a word no line starts with fails the load. The slot only names the lines: a rule on it fails the load, and the judge's role comes from the line's slot. `JudgeRule.primitive` is now `primitives: string[]` (empty for `{line}`).
- **A name means one thing to an agent.** A variable or a constant never shares the name of a template the agent sees — the build fails, naming both. Reading a template as a variable (`{{qa-report}}`) fails with *`qa-report` is a template, not a variable*.

### Fixed
- **`{other.EXAMPLE}` in a template's `EXAMPLE` composes again in compiled agents.** The marker was resolved only on the old template path; an agent compiled through the document printed it as is. Now the document's templates resolve it (`MdEnv.exampleOf`, the same `composeExample` both paths use), with the same errors: an unknown template, one with no `EXAMPLE`, a loop.
- **A loop's rounds start again after its limit.** A checked `UNTIL` (and an `UNTIL*` / `UNTIL**`) counted every closed answer of a session in a row: a flow that entered the same loop once per task read `round limit reached (4 of 3)` on the second task. A check made after the limit now starts a new loop at round 1, as an open answer already did.
- **`set` of a typed variable refused shows the shape it takes.** Beside *the value is not shaped as `x`: …*, the apx prints `# the JSON `x` takes: {…}` — the template's example, so the next try is the right one instead of a guess.

The help and the build open with agent-pack.org's logo in its own pixels and colours — the mascot beside the wordmark on a wide terminal, above it otherwise, filled cells as backgrounds and half cells as half blocks, each run of one colour written as one piece so a terminal draws it with no seam — then the version, marked *pre-release* before 1.0 (`--version` says so too), what agent-pack does, its author, licence and site; the help adds the docs and where to report issues. - **A dimension is reached by its id: `dimension <dim-id> <verb>`.** Like every other block, a dimension is addressed by the id its compiled line carries (*use the dimension `knowledge` (dim-…)*): `dimension <dim-id> read|write|find|ls|why|clear|gc …`, and `dimension` alone lists the agent's dimensions with their ids — it replaces the verb `dims`. Reaching a dimension by its name is gone, and so is the rule that a dimension may not be named like an apx verb or a store (a store is still reached by its name). New verb `dimension <dim-id> find <text>`: every instance kept across the dimension's files whose text holds `<text>`, fresh entries only — the one way to look across files.

The limit travels with the check (`meta.checks[id].rounds`) and with the executor's contract. A missing `MAX`, `MAX 0`, `MAX many`, a `MAX` on a plain `UNTIL` (the agent ends it) or on any `IF` fail the build, from the document builder and from the source scan of flows.ap and standalone files alike (`maxIssue`, `src/check.ts`). The config key `checks.rounds` is gone — a config that still sets it fails with the line to write; `bundle all` no longer records a round limit in the `.apx`.
- **`TAGS` is now `APPLIES`.** The line that tags a block is written `APPLIES #a #b`, on every kind of block, with the same grouping, filtering and judge tags as before; on a policy it also takes the policy's scope (`universal`, `team:<team>`, `agent:<agent>`). Rename `TAGS` to `APPLIES` in every source.

- **A variable is seen only where it is declared or imported — imports never pass on.** `{{x}}` reads a variable the body declares or the file itself imports; a variable a procedure or a role imports is that module's, not the agent's — reading it there fails, naming the file that imports it. ## [0.28.0] - 2026-10-12

### Added
- **Executors (I2) — `DO` the agent, `ASK` a delegate, `COMPUTE` a program.** The verb says who carries a line out; on a block head, stars say the same: `PROCEDURE*` / `PROCEDURE**` hand the whole body to a delegate / a program, `IF*` / `UNTIL*` and `IF**` / `UNTIL**` only the condition (the lines beneath inherit the enclosing block's executor). A line may raise its executor (agent → delegate → program), never lower it: an `ASK`, an `IF*` or a `RUN` of a lesser procedure under a `PROCEDURE**` fails the build, and so does a checked condition (`IF!`) inside a starred procedure. A condition has one judge: `IF!*` / `UNTIL**!` is an error. A starred condition reads at least one variable. `ASK` and `COMPUTE` take `INTO` like `DO`.
- **`ASK … BY <agent>` and the default delegate `quick`.** `BY` ends the line (after `INTO`) and names a standalone agent, a team, or a member of the asking agent's own team — another team's member or an unknown name fails the build; `COMPUTE` takes no `BY`. Without `BY` the line goes to `quick`, a builtin agent (`templates/agents/quick.ap`) that answers from its JSON input alone, as JSON in the contract's shape; `bundle all` builds it only when some agent hands it work and the project has no agent of that name. With Claude Code it runs on `haiku` with `tools: []`.
- **Config key `delegate`** — `{ default, models }`: the agent an `ASK` without `BY` goes to (`quick` by default) and the model each agent runs on, by name (Claude Code's `model:`; `inherit` otherwise). The source never names a model.
- **`COMPUTE <name>:` blocks.** A procedure a program carries out, written as a specification: rule lines on top (how the program is written), then `REQUIRE:` (when it refuses — rules and `IF`), `RETURN AS <template>:` (the computation and its result's shape — `DO`, `COMPUTE`, `IF`, `UNTIL`, rules, never `ASK`; no force level on the `AS`) and `ENSURE:` (guarantees, which become tests) — all three required, non-empty, in this order. It is a `PROCEDURE**`: run with `RUN`, importable, judged like any other lines.
- **Contracts, `meta.executors`.** Every piece a delegate or a program carries out gets an id `exe-<8 hex>` and a contract in the compiled document: its input (the variables it reads, the constants with their values, `in` for a `LENS-IN`), its output (the `INTO` variable and its template, the procedure's `AS`, or `holds` for a condition), `rounds` for an `UNTIL`, and for a program its folder (`dst-…`) and `lineage`. New node fields: `by` and `exe` on `ASK`/`COMPUTE` directives, `executor` and `exe` on starred `IF`/`UNTIL`, `executor`, `exe`, `require` and `ensure` on procedures; `meta.delegate` and `meta.model`.
- **apx verbs `input`, `answer`, `run`.** `input <exe-id>` prints the JSON a piece receives, and nothing else (an empty variable stops it). `answer <exe-id> -` takes a delegate's answer, checks it against the contract, stores it in its `INTO` variable and records it; an answer that breaks the contract is refused (exit 6). `run <exe-id> [in-json]` runs a program — exit 10 no program yet (the message says where and how to write it), 3 refused (stop the procedure), 4 timeout (the agent does this one run, and says so), 6 broken or failing its own tests. `--into <var>` on `answer` and `run` stores a procedure's result in a variable. `get <exe-id>` shows a contract, `scope` lists them. Each answer and run is recorded in `.agent-pack/state/<session>/executors.tbl` (contract, executor, who, input fingerprint, outcome, `holds`, time).
- **Program folders and their tests.** A program lives at the project root in `distilled/dst-<8 hex>/`: `manifest.json` (`version`, `previous`, `lineage`, `timeout_ms`; the apx writes `tested`), `script.<ext>` (JSON on stdin, JSON on stdout, exit 1 to refuse) and `tests.json` — cases `{why, input, output}` or `{why, input, exit: 1}`, with a `why` starting `CHOICE:` for each decision the block left open. The agent writes it at the first `run`, following the builtin procedure `write-program` (imported by every agent a program works for). A new or changed program runs its tests before it is used. An edited piece gets a new folder that starts from the previous version; `bundle all` reports orphan folders, never deletes them. An agent's perimeter includes `distilled/**` when a program works for it.
- **`RUN p INTO x`.** A procedure's result goes into a declared variable, typed by the procedure's `AS` (a mismatch fails the build) — like `VAR x:` with `RUN p` beneath, which stays valid. When a delegate or a program carries `p` out, the apx stores it (`--into x`).
- **Round limit for `UNTIL*` / `UNTIL**`.** The condition is asked after each round, at most the rounds the head writes — `UNTIL* <condition> MAX <n>:`, required, as for `UNTIL!` (see *`MAX` on every loop someone else ends* under Changed); the apx says `round n of N` and, at the limit, to stop and report that the condition never held — with exit `7`, so a command chained after it never starts another round.
- **`SHOULD-NOT`** — a force alias, `SHOULD` at level −1 (*You should not*): a warning, usable wherever `SHOULD` is.
- **Scoped and negative judge rules.** A `#judge` template tagged `#executed` judges only the lines a delegate or a program carries out, `#program` only a program's, `#agent` only the agent's own; an `#executed` / `#program` rule may lay out `{line}` alone and judge every line of its scope. Negative rules (`NEVER`, `MUST-NOT` an error, `SHOULD-NOT` a warning) are asked directly; `YES` / `NO` lines under a slot rule give the judge's criteria; `EXAMPLE` lines `<line> → <verdict>` are reference examples. Such a rule sends a JSON state — the line with its reads as plain names, its inputs' names, the slot's description, the examples. The language tags are exempt from the library index's tag-similarity check.
- **Three builtin judge rules.** `judge-executed-inputs` (`#executed`, error: a line handed away relies on nothing but its inputs and its own words), `judge-program-vague` (`#program`, error: a program's line leaves nothing to guess — a rounding mode, a threshold, a tie rule) and `judge-compute-suggestion` (`#agent`, `SHOULD-NOT` warning: a `DO` line that is a plain calculation — consider `COMPUTE`). **With `judge` on, the text of the lines these rules judge — `ASK` lines, starred conditions, starred procedures' bodies, `COMPUTE` sections — is sent to TypeSafe too.**

### Changed
- **`INTO` ends a `DO`, `ASK`, `COMPUTE` or `RUN` line** — `RUN … INTO` was an error.
- **The judge's builtin rule set is six rules**, and a rule's `BODY` no longer has to start with a keyword when the rule is tagged `#executed`, `#program` or `#agent`.

### Removed
- **`DISTILL`** (spec D22) and its levels (`DISTILL!`, `DISTILL!!`, `!DISTILL`), with `src/distill.ts` and the `distill` node. A source using it fails with *DISTILL was removed — mark the procedure PROCEDURE\*\* or write a COMPUTE block*. `apx run` takes a contract id (`exe-…`), no longer a `dst-…` script id; scripts move from `distilled/<id>.<ext>` to program folders `distilled/<dst-id>/`.

### Fixed
- **A role's `IMPORT`s are resolved.** The templates, policies and procedures a library role imports — at the top of its file or in its body, and those of the roles it `EXTENDS`, also from an inline role — now enter the agent like the agent's own imports. Before, they were missing from the agent and their `IMPORT` lines were left as text in its identity.

## [0.27.0] - 2026-10-06

### Added
- **Checked conditions — `IF!`, `IF!!`, `UNTIL!`, `UNTIL!!` (I1).** The `!`s after a condition head say who decides it: `IF!` — the agent sees the condition, a judge decides it and wins; `IF!!` — a gate: the condition is sealed (in no prompt, no apx view) and the agent hears only open or closed; `UNTIL!`/`UNTIL!!` repeat until the gate opens, at most the rounds the head writes (`MAX <n>`, required). `!IF` is an error. A checked condition reads at least one variable (`{{x}}`, or `{{x AS t}}`, whose template's fields guide the judge); its question (`In the state, <condition>?`, constants written in) is built at compile time and kept in the document's `meta.checks` under a stable id `cnd-<8hex>` (the answering agent + the condition's text). New apx verb **`check <cnd-id>`**: builds the state from the session's variables (`### <name>` + the value as stored), asks the judge one question, answers `open` (p ≥ threshold, exit 0) or `closed` (exit 1; 2 on a usage or config error) — closed when in doubt: below the threshold, an empty variable, a state too large for the judge, a judge that cannot answer, no session id. A checked `UNTIL` counts closed rounds per session, agent and condition; every check is recorded in the session (`checks.tbl`, behind the variables seam) with a fingerprint of the state, never the state. In a flow `STEP`, `IF!`/`IF!!` is checked by the step's `BY` agent through its own apx (`AGENTS.md`, `apx flow` and the Workflow script name it); `BY` a team, or a checked condition at a flow's own level, fails the compilation (the latter: not supported yet). Where no executable answers — a playbook, a team's routing — `IF!` reads as `IF` with a warning and `IF!!` fails. One rule decides all of it (`condCheckOf`, `src/check.ts`), for the document builder, the md of `AGENTS.md` and playbooks, and the source scan of flows.ap and playbooks. A step's `BY <role>` now names the member bound to that role in the member's document too, as `AGENTS.md` already did. New config key **`checks`** (`adapter`, `threshold` 0.7), apart from `judge`; without it `IF!` falls back to `IF` with a warning and `IF!!` fails. `bundle all` records the judge's name, threshold and the model the judge lock pins in every `.apx`. `JudgePlugin` gains an optional `maxStateChars` (`jev`: 96 000) and a check may carry its own `question`, asked as is. **With `checks` on, each check sends its question and the variables it reads to the judge.**
- **Variables (I7), private or shared by the session.** `VAR` names values known at compile time or produced while the agent works. `VAR x` declares a variable private to the agent (the default — no keyword), `SESSION VAR x` one every agent of the project shares for the session; `GLOBAL VAR x` is reserved (an error: not available yet). A scope word stands only right before `VAR`, never on a constant. Private variables are declared in the agent's own `vars.ap` or in the body of an agent, a role or a procedure (a procedure's belongs to the agent running it); `SESSION` ones only in a team's or the project's `vars.ap`. `VAR x AS <template>` types one; `VAR x:` with an indented block declares it and assigns it the block's final outcome (DO lines, a `RUN`, an `IF`/`ELSE`, an `UNTIL`, rule lines, `IN`) — or, when a `vars.ap` already declares `x`, only assigns it: how a procedure's result goes into a `SESSION` variable. `DO … INTO x` — a trailing, uppercase `INTO` on a `DO` line — assigns a declared one. A name is declared once per agent, in one scope: a second declaration, or a private variable named like a `SESSION` one (shadowing), is an error. A variable keeps one type: its template, or the result template (`AS`) of the procedure its block runs; a mismatch, or an `IF` and `ELSE` yielding different types, fails the compilation, and every step that fills a typed variable is told to shape its result as the template. `{{x}}` of a variable compiles into the apx command that prints its value. In the document a variable is a block of kind `var` (`var-…`, namespace `@main.vars`, `args.scope`); a `VAR x:` block is a `var` node, a `DO … INTO` directive carries `into`.
- **Shaped reads, `{{name AS template}}`.** A read of a variable can take a template's shape: the compiled line tells the agent to read the variable through its apx and keep only what fits the template, shaped as it (`VAR.readShaped` in the formulas). Nothing is stored. A variable already typed with that template reads plain. A constant, an unknown template or `AS!` fail the build; the rules of plain reads apply (not in a template's text, not from a shared library's block, not in a playbook). The read pattern of `src/vars.ts` carries it — `readsOf` gives every part of a read.
- **`apx get <name>` / `apx set <name> -|<value>`.** `get` shows a variable — its scope, type, where declared, who stores it, who reads it — then its value in this session, byte for byte; `set` stores it (stdin with `-`), refusing a constant, an undeclared name, and for a typed variable any value that is not JSON its template accepts. Both find the scope themselves: a private value is the agent's alone (kept across its invocations in the session), a `SESSION` value one for every agent of the session. `get` and `set` are the only way to a variable; where the values are kept sits behind one seam of the apx (`src/apx/sessionVars.ts`) — today tabeli tables under `.agent-pack/state/<session id>/`. The session id comes from the environment variable the adapter declares (`AdapterPlugin.sessionEnv`; `claude-code`: `CLAUDE_CODE_SESSION_ID`, recorded as `meta.sessionEnv`); without it, variables fail closed. `ls kind=var` and `scope` list the variables with their scope. A playbook takes no variable yet (it has no executable): a `VAR`, a `DO … INTO`, a read of a variable fail its compilation.
- **`vars.ap` at three levels**, project < team < agent: a deeper constant overrides the one above it.
- **The judge — a compile phase in which a model checks that `.ap` code is well written.** A rule is a `TEMPLATE` tagged `#judge`: its layout names the lines it applies to, its slot rules are the checks, `MUST` an error and `SHOULD` a warning. The three builtin `#judge` rules check every `DO` line: `judge-do-line`, it holds exactly one imperative verb; `judge-do-condition`, it carries no condition — a condition is an `IF` line with the `DO` under it; `judge-do-force`, it opens with no word of force — a force level is written with its primitive (`NEVER`, `ALWAYS`, `MUST`, …). The `jev` judge (TypeSafe AI, key from `TYPESAFE_API_KEY` or `~/.config/typesafe/key`) answers one request per distinct line; diagnostics land at `file:line:col` with the check id; the decisions live in the lock `agent-pack.judge.lock` (the judge, its model pinned on the first answer, human verdicts that win over the judge's, whatever the model — a clean `bundle all` lists in one line the decisions no line used, never deleting them) and the judge's work in one unit per `.ap` source, `.agent-pack/units/<source>.json` (like a C object file: the source's hash, the rules' hash, the model that answered, its verdicts by hash, its diagnostics; a library source outside the project goes under `_external/@alias/<path inside the library>.json`, any other under `_external/<dir hash>/<file>.json` — no machine path is written) — a source whose text and rules did not change is not judged again, an edited one asks only for its changed lines, a model changed in the lock reuses no verdict of another model, a single-agent `bundle` keeps a unit's earlier verdicts, a clean `bundle all` trims what it re-judges and deletes the units of sources no agent uses any more. New config key `judge` (`adapter`, `threshold`, `offline`, `lock`, `concurrency`) — absent, nothing changes; flags `--no-judge` and `--judge-strict`. **With `judge` on, the text of the `DO` lines is sent to TypeSafe.**
- **`IF` / `ELSE` inside a flow `STEP`.** A step may put some of its `DO`/`RUN` lines under `IF <condition>:` and its `ELSE`; `BY`, `CONTEXT` and `AS` stay unconditional. The step is valid when its only `DO` sits under the branch. The lint, the document (`lines()` with containers `[step, if]`), `AGENTS.md`, `apx flow` and the Workflow script carry the branch.
- **Rule lines in procedures and flow steps.** A `PROCEDURE` (at its top and under its `IF`/`ELSE` and `UNTIL`), a `STEP` and a step's `IF`/`ELSE` branch take the force-level families roles and playbooks take — `MUST`, `ALWAYS`, `NEVER`, `SHOULD`, `MAY`, their `!`/`!!` forms and aliases (`AS` in a branch and `DISTILL` in a step stay rejected; `MEM` is a procedure's, never a step's — see Changed) — so `DO never …` / `DO always …` become `NEVER …` / `ALWAYS …`. A rule line is not an action: a step still needs a `DO` or `RUN`. The lines become directive nodes with their force, render in source order in `AGENTS.md`, `apx get`, `apx flow` and the Workflow script, and appear in `lines()` with their positions. Existing sources compile byte-identically.
- **`IF` / `ELSE` and `UNTIL` in a `FLOW`.** A flow may put some of its `STEP`, `PARALLEL` and `RUN` lines under `IF <condition>:` and its `ELSE`, or repeat them under `UNTIL <condition>:` — a fix-round or plan-revision loop — and nest further `IF`/`ELSE`/`UNTIL` inside them. No new keyword: the condition is prose, judged by whoever runs the flow, and an `UNTIL` takes no mandatory bound. A flow still needs a `STEP`, directly or under a branch. This makes legal what the builder already compiled and `AGENTS.md` already rendered.
- `LintError` carries an optional `col`, `endCol`, `code`, `source` and `data`; diagnostics print `file:line:col` and `[code]` when known.
- **A flow runs as the harness's own script.** An adapter may declare `flowScript`: `bundle all` then compiles every flow into `.agent-pack/flows/<id>.<hash>.<ext>`. The claude-code adapters compile a Claude Code Workflow tool script — each `STEP` an agent of its `BY` type, `PARALLEL` a parallel group, upstream results passed by `CONTEXT` mode, a step's input `AS` enforced as the JSON Schema of the answer that feeds it. A flow run by a team, or holding anything but steps, keeps its prose.
- **`apx flow <flw-id>`** — how to run a flow: the adapter's instruction (`renderings.FLOW.run`) with the script's path when a script exists for this version of the flow, its steps otherwise. `AGENTS.md` routes every flow through it (`Run the flow … — start with \`node <member>.apx flow <id>\``), so the file stays harness-neutral. In the apx views a flow is reached by `flow`, not `get`.
- **The claude-code-apx agent file carries the agent's own definition.** Before pointing at the apx, `.claude/agents/<name>.md` now holds the agent's preamble — perimeter, team, identity, mandate, request and answer shapes, its own rules — in the same words as the `claude-code` file and `apx get <agent>` (`ApxEngine.definition()`), every reference as the apx command that fetches it. Policies, templates, procedures, stores and flows stay in the apx, read on demand.
- **`jsonSchemaOf`** (`src/shapeSchema.ts`) — a template's slots as JSON Schema, from the same grammar the validator checks; `ApDocument.slotsOf` / `slotResolver` give the apx and the adapters one way to read a document's templates.
- Community health for the public repository: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), `SECURITY.md`, issue and pull-request templates, and a CI workflow (build and test on Node 20 and 22).
- `package.json` declares `repository`, `homepage`, `bugs`, `keywords` and `engines` (`node >= 20`).
- **tabeli ships with agent-pack** (`tabeli/`, MIT — its engine, tests, docs and Claude Code skill packaging), so the two evolve together. `npm run build` compiles the engine with tabeli's own Makefile (`tabeli/tabeli`; building now needs `make` and a C compiler, and says so when none is found), and `npm test` runs tabeli's suite too — its v1-upgrade tests against the last v1 engine, vendored as `tabeli/test-fixtures/tabeli-v1.c`. The npm package carries the engine's source, Makefile and license and builds it on install.

### Changed
- A block of a shared or builtin library may not read a session variable — it takes its input through `LENS-IN`; constants are unchanged.
- **The apx runs the tabeli engine agent-pack builds**: `bundle all` records its path in every `.apx` (the build provenance), instead of looking for the tabeli skill in `~/.claude/skills`. An `.apx` written before records none — rewrite it with `agent-pack bundle all`.
- The apx creates a tabeli table — a store's too — only with a tabeli engine v2 or newer (v1 stored values lossily); a table created earlier keeps running the engine it carries. A store's `KEY` upsert reads tabeli's JSON answer instead of its text.
- A playbook's own file goes through the vocabulary check when it is compiled, like an agent's.
- `apx get <arg>`: an argument shaped like a block id is a block, as before; any other is a variable. The not-found error now reads `no block with id '<arg>' and no variable named so`.
- **A team's `flows.ap` takes the flow contracts a flow file takes.** Its `FLOW`, `STEP` and `PARALLEL` blocks are checked like those of a flow file: a step needs a `DO` or `RUN` (`BY` and a rule line alone are rejected), `AS` under a step's `IF` is rejected, and so is any line a flow, step or branch does not admit. Every team `flows.ap` in this repository lints clean.
- **An `AGENT` takes rule lines at every force level at its top**, from the same family list procedures and steps draw from: `SHOULD`, `MAY` and `MEM` (and their `!` forms) join `ALWAYS`, `NEVER` and `MUST`, instead of reaching an agent only through a `WHEN` or its role. `DISTILL` stays rejected there, with its reason — it marks a procedure, never an agent. The other agent rules are unchanged; existing sources compile byte-identically.
- **`MEM` is no line of a flow `STEP`, nor of its `IF`/`ELSE` branches**, like `DISTILL`: the agent a step's `BY` names may have no memory in its harness. The lint says so at the line; `MEM` stays legal in agents, roles, `WHEN` blocks and procedures.
- **The judge goes offline only when it cannot be reached or refuses the caller** — unreachable, timed out (30 s), no key, or key rejected (401/403). Any other failure — a 429, a 5xx, a 400, a malformed answer — leaves only that line "not judged yet", with its own reason, and the rest of the queue is still asked; `jev` retries a 429 or 5xx once. A judge object marks such a failure with an error whose `kind` is `'line'`. The summary counts distinct lines and rule × line checks apart, and how many were not judged.
- `bundle all` says when it finds no agents, instead of reporting only an empty orchestration.
- `--help` lists `--apx-compress`; the CLI reference documents `--version`.
- The README and the getting-started guide install from source until the npm package is published, and create `agents/standalone/` before copying an example; the README's first agent compiles on its own.

### Removed
- `APX_TABELI` and the lookup of the tabeli skill's `ensure-engine.sh`: the apx has one engine, the one agent-pack builds.
- The `RETURN` keyword, which nothing compiled any more: a `RETURN` line is now an unknown keyword.

### Fixed
- `{{a-b}}` — a hyphenated variable name — was never checked nor substituted; variable names take hyphens like every other name, through one shared pattern.
- `vars.ap` is linted: a malformed line, a duplicate name, a name shaped like a block id fail the build; `VAR x` without `=` was silently skipped.
- `{{…}}` in a template's `BODY` or `EXAMPLE` (literal text, never substituted) and `{{x.field}}` (not supported yet) fail the build; a comment line is no longer checked for undeclared variables.
- A `STORE` named like an apx verb (`set`, `ls`, `get`, …) fails the build: the apx read the verb and the store was unreachable.
- A `DISTILL` line directly in a `PROCEDURE` of a procedure file no longer raises a lint error.
- An `ELSE` not right after an `IF` in the same body is a lint error, instead of compiling as unconditional lines.
- A flow file whose header ends in a colon (`FLOW ship:`) no longer warns that its name does not match the filename.

### Security
- `js-yaml` raised to `^4.3.2` (quadratic-CPU advisories on merge keys and `!!omap`).

## [0.20.0] - 2026-06-10

### Added
- **Typed TEMPLATE contracts** — a template body may declare `SLOTS:` / `BODY:` / `EXAMPLE:` regions: typed slots (`TEXT [MAX_WORDS n | MIN_WORDS n | REGEX /p/]`, `NUMBER min..max`, `ENUM[a b c]`, `<tpl>`, `LIST <tpl>`), a literal `BODY` layout with `{slot}` placeholders, and a few-shot `EXAMPLE` rendered inside `<example>` tags. Constraints render as guidance only (enforcement deferred to a future MCP validator for `strict` templates). Scalar shorthand: `TEMPLATE name: TYPE … "desc"`. Prose templates keep rendering verbatim.
- **Slot-scoped rules** — force-level lines under a slot attach to it lexically (order + uppercase keyword; indentation is style, not semantics). An orphan rule fails the bundle. Rendered as calibrated sub-bullets under the field legend.
- **Template composition** — a slot may reference another template (`<tpl>` / `LIST <tpl>` resolve to `§N.M` through the AS resolver), and a `.template.ap` file may `IMPORT` the templates it composes (transitive imports, e.g. `idea-verdict` → `score-row`).
- **`LENS <template>` agent key** — binds the agent's response shape to an imported template; sugar over a standalone `AS!` line, rendered right after the Identity block. At most one per agent.
- **Step output contracts in flows** — a flow `STEP` may declare `AS <template>` (any force-level declension: `AS` / `AS!` / `AS!!` / `!AS`) as the step's output contract — i.e. the next step's input format. The orchestration context now resolves project libraries, so a team `flows.ap` can import the templates its steps bind.
- **Centralized verbatim guard** — `markVerbatim` / `protectVerbatim` (services/text) shield `BODY` and `EXAMPLE` content from every post-emit rewrite pass.
- **product team** — `concept-shaper` (severe idea evaluation through the `idea-verdict` scorecard, composed of `score-row`) and `pm` (`pm-plan` Gantt), wired via the `shape-idea` flow with per-step shape contracts.

### Removed
- **LENS kind** — retired: a response shape *is* a TEMPLATE. The two prose lens files migrated to templates; the builtin `default` lens, the Response-lenses chapter, the `.lens.ap` extension, and `ensureDefaultLens` are gone. `lens` no longer appears in registries, contexts, or resolvers.

### Changed
- **Templates chapter intro** rewritten for the typed model (fill the layout, `{slot}` placeholders, constraints as self-enforced guidance, imitate `<example>`); **Flows intro** gains the step shape-contract rule.
- **Lint** — `.template.ap` accepts `IMPORT` (composition); `agent.ap` accepts `LENS` (≤ 1); template header tolerates the `TEMPLATE name:` block-opener form.

## [0.19.0] - 2026-05-29

### Added
- **`AS <shape>` operator** — declares a procedure's output shape, replacing the `RETURN AS` form. Documented in `file-kinds.policy` (`.procedure.ap` carries an optional `AS <shape>`).
- **Per-team FLOW in orchestration routing** — a team's `team.ap` now resolves through the same bundle pipeline as every other source, so an inline `FLOW`/`PROCEDURE`/`TEMPLATE` declared under `routing:` renders identically to one declared in an agent. Each team renders its own collected sections in an isolated child context (shared vocabulary, fresh numbering, no default-lens injection).

### Changed
- **Single source-body resolution** — every bundle path (agent, playbook, standalone, orchestration) now goes through one `resolveInlineBlocks` helper (`expandImports` → `extractInlineDefinitions`), so inline blocks hoist identically regardless of which file declares them.
- **Inline-block lexer** accepts the colon-less `FLOW <name>` opener alongside the `PROCEDURE name:` / `TEMPLATE name:` forms.
- **Control-flow rendering** adds `STEP` (→ `Step`) and `PARALLEL` (→ `In parallel`) heads.

## [0.14.0] - 2026-05-06

### Added
- **Indent-aware lexer** (`src/lexer.ts`) — single source of truth for `.ap` keyword recognition. Emits one classified token per line with `line`, `col`, `indent`, `keyword`/`rest`, `raw`. Replaces the per-pass regex scanning in lint, body rendering, metadata extraction.
- **Declarative lint engine** — `runLint(spec, …)` driven by `LintSpec` per file kind (policy/playbook/procedure/persona/template/vocabulary). Six specs share one walker; reusable handler factories (`accept`, `counts`, `flags`, `triggerHandler`, `ifElseHandler`, `headerHandler`, `checkHeaderCount`).
- **Primitive-driven body rendering** — every keyword that produces structured output is now a `PrimitiveStrategy`:
  - `WhenPrimitive` — playbook trigger with adapter-claim (claude-code → `when-to-use:` frontmatter; multi-WHEN supported).
  - `RunPrimitive` (`RUN <procedure>`) — replaces legacy `@<name>`. Inline rendering for ≤ 3 procedures (`Run procedures \`a\`, \`b\`, \`c\` (in order)`), bullet list for more.
  - `DoPrimitive` (`DO <action>`) — replaces legacy `STEP`.
  - `TermPrimitive` (`TERM <name> := <gloss>`) — vocabulary entry; renders as `\`name\` : gloss`.
  - All force-level keywords (`MUST`, `MUST!`, `MUST-NOT`, `SHOULD`, `SHOULD!`, `MAY`, `ALWAYS`, `NEVER`, `NON-NEGOTIABLE`) generated via `createBulletGroupPrimitive` factory.
- **Real `contributesFrontmatter` contract** — adapters obtain frontmatter fields by walking primitives and aggregating their contributions (`collectFrontmatter` + `serializeFrontmatter`). Eliminates the prior sentinel-based "claim" signal.
- **`bundle.metadata: Map<Keyword, string[]>`** — single uniform store replacing scattered `description`, `ownsGlobs`, `whens` fields. Aggregates across multi-file agent sources via `mergeMetadata`.
- **`SectionSpec`-based emission** — `emitChapter(ctx, spec)` renders Vocabulary, Personas, Templates, Procedures, Tools, Memory uniformly via two modes (`renderFlat` / `renderEntry`). Replaces 4 ad-hoc emitters.
- **`partitionMetadata`** — single-pass extract + strip per source file (replaces chained `extractPrimitive` + `extractPrimitives` + `stripPrimitives`).
- **`applyBodySubstitutions`** — fused regex pass for `{{var}}` + `RETURN AS` + `$term` (was three sequential passes).
- **`stripHeaderKeyword`** — strips redundant `TEMPLATE <name>` / `PROCEDURE <name>` line from collected entries (the section heading already names the entry).
- **`renderControlFlow`** — `IF`/`ELSE` rendered as `If <cond>:` / `Else:` (case-fold + trailing colon, Python/YAML idiom).
- **Vocabulary refs `$term`** — `$<name>` in playbook prose expands to `` `<name>` `` when `<name>` is a registered TERM.
- **`# Steps for <playbook-name>`** header — playbook procedural body labelled distinctly from declarations chapters. Declarations (Vocabulary / Templates / Procedures) emitted **before** the Steps so every reference is defined when the LLM reads the entry point.
- **`injectNeutralIfUnclaimed`** — shared body-vs-frontmatter decision for OWNS (agent) and WHEN (playbook); the primitive `contributesFrontmatter` decides, the bundler stays generic.

### Changed
- **DSL syntax migration** (breaking for sources, adapters unchanged):
  - Vocabulary `TERM <name>: <gloss>` → `TERM <name> := <gloss>` (assignment idiom; `:` reserved for the gloss text).
  - `STEP <action>` → `DO <action>` in playbooks and procedures.
  - Procedure invocation `@<name>` → `RUN <name>`.
  - All built-in `templates/library/...` files migrated.
- **Bundle pipeline** centralises keyword recognition through the lexer (lint, metadata extraction, body rendering, primitives all share one tokenizer; previously 7+ regexes lived in different files).
- **`NON-NEGOTIABLE` intro compressed** ~50% (`[IDENTITY CONSTRAINT] Before any other action, no exceptions; output skipping this is invalid:`); precedence + output-invalid clauses preserve the gap with `MUST!`.
- **Library relocation** — built-in agent library moved from `agents/library/` to `templates/library/agents/library/` (consistent with the `templates/library/` runtime convention).
- **Lint** — relaxed the "playbook must have exactly 1 WHEN" rule; multiple triggers are now supported and emitted as a list in claude-code `when-to-use:`.

### Fixed
- Playbook H1 (`# <name>` from source) is replaced with `# Steps for <name>` so the chapter is unambiguous and distinct from declarations.
- Top-level vs indented metadata extraction — `ABOUT`, `OWNS`, `WHEN`, `TERM`, `IMPORT` now match only at indent 0 (prevents false positives on `IMPORT` lines inside markdown code fences in playbook prose).
- `processImports` byte-equivalence — state-machine token-join replicates the legacy `\s*$` greedy behaviour around IMPORT lines (consume trailing blank line). Bundles produced by 0.14.0 are byte-identical to 0.13.0 for the same source modulo the deliberate format changes above.

### Removed
- `src/returnAs.ts` — folded into `applyBodySubstitutions`.
- Legacy `STEP` keyword — removed from lint regexes (sources migrated to `DO`).
- Sentinel `renderFrontmatter` returning `{ '<KEYWORD>': '<emitted-by-adapter>' }` — replaced by typed `contributesFrontmatter`.

## [0.12.0] - 2026-04-23

### Added
- `delegate` MCP tool — spawn headless Claude subagents from registered agents; sub-tasks are dispatched with an `agentName` and a high-level problem statement, letting the target agent run its own bootstrap lifecycle.
- `persona` primitive — 4th cognitive layer of an agent definition, sits alongside IDENTITY / SOUL / WORKFLOW.
- `vars` substitution — `{{key}}` placeholders resolved at bundle time and during `@import` expansion.
- `force level` system — bundle-time expansion of calibrated obligation keywords (`MUST`, `SHOULD`, etc.) into consistent prose formulas for clearer LLM parsing.
- `wiki-notion` plugin — Notion API as a wiki backend for the `@wiki` directive.
- Rule grammar — structured lint rules in `src/lint.ts` with reference documentation at `docs/reference/rule-grammar.md`.
- Runtime auto-injection — framework rules and built-in phases included automatically in every bundle without explicit `@import`.
- Orchestration rules and agent roster injected into `CLAUDE.md` by the `team init` command; agents are read from the project manifest at inject time.
- README.md with project pitch.

### Changed
- Agent library restructured: `task-runner` added, `typescript-senior` renamed from `senior-typescript`, `product-manager` dropped from built-in agents.
- `ABOUT` section stripped uniformly via shared `text.ts` across all compilation paths (CLI bundle, MCP tool, entrypoint generation).

## [0.9.0] - 2026-04-16

### Added
- `lens` primitive: reusable response formats stored in `agents/library/lenses/<name>.lens.ap`. The bundler reads `lenses` declared per-agent in the source manifest and, when `callerAgent` is supplied, injects the intersection of caller and target lenses into the compiled prompt as a `## Response lenses` section.
- `callerAgent` parameter on the `bundle` MCP tool and matching `--caller` flag on the CLI.
- `populate-claude` command: scans `agents/definitions/` plus `PREDEFINED_AGENTS`, regenerates `.claude/agents/<name>.md` entrypoints, writes `.claude/agents/manifest.yml`, and removes orphan entries. `--override` wipes destination first.
- `sourceManifestPath` config (default `agents/manifest.yml`): decouples the agent-pack source manifest from the Claude-facing manifest so lens declarations stay out of `.claude/`.
- Built-in `product-manager` agent definition under `agents/definitions/product-manager/` and `user-stories` lens under `agents/library/lenses/`.

### Changed
- Default `agentsDir` is now `agents/definitions` (was `.claude/agents/definitions`). Agent sources live alongside `agents/library/` and `agents/manifest.yml` at the project root; `.claude/agents/` is generated output.

## [0.10.0]

### Added
- Typed plugin system. Plugins are declared in `agent-pack.config.mjs` via the new `plugins` field and validated by a registry that checks `apiVersion`, type, and uniqueness.
- `WikiPlugin` contract (`src/plugins/types.ts`) with capability negotiation: `name`, `path`, `tag`, `backlinks`, `frontmatter`, `search`. Implementations declare which lookups they support; the bundler refuses to call methods not declared.
- Built-in `wiki-fs` plugin (`src/plugins/builtin/wiki-fs.ts`) backing the filesystem with `path` and `name` capabilities. Indexes basenames with an mtime-keyed cache.
- Built-in `wiki-obsidian` plugin (`src/plugins/builtin/wiki-obsidian.ts`) backing an Obsidian vault with all six capabilities (`path`, `name`, `tag`, `backlinks`, `frontmatter`, `search`). Parses frontmatter aliases and tags, extracts inline `#tag` and `[[wikilink]]` patterns from bodies (excluding fenced code blocks), builds an inverse index for backlinks, and supports optional recursive `![[embed]]` expansion with cycle detection and depth cap.
- New `@wiki` directive recognised by the parser. Forms: `<!-- @wiki "Note Title" -->`, `<!-- @wiki path="..." -->`, `<!-- @wiki name="..." -->`, `<!-- @wiki tag="a,b" -->`, `<!-- @wiki linksTo="..." -->`, `<!-- @wiki where="key:val ..." -->`, `<!-- @wiki search="..." -->`. Optional props: `provider`, `limit`, `format`, `depth`, `tagMode`. The bundler dispatches to the active wiki plugin and emits inline error comments on capability mismatch or missing provider.
- `defaultWikiProvider` config field to disambiguate when multiple wiki plugins are registered.
- `tagMode` option on `WikiOpts` (`'and'` default, `'or'` opt-in) to control tag intersection vs union.
- Directive handler pattern: 5 dispatchers (`dispatch/file.ts`, `dispatch/directory.ts`, `dispatch/tool.ts`, `dispatch/memory.ts`, `plugins/wiki-dispatch.ts`) each implementing a uniform `DirectiveHandler` contract. `bundleAgentToString` uses a Map-based lookup instead of an if/else chain.
- `getDirectiveRegex()` exported from `src/parser.ts` — centralised regex construction from a `DIRECTIVE_NAMES` list, returns a fresh instance per call (no shared state).
- Shared `collectFiles` helper in `src/utils/fs.ts`.
- New `agents/` directory at the repo root with a dedicated `senior-typescript` agent definition (IDENTITY/SOUL/WORKFLOW) for future self-development of the core.
- Test suite for the plugin system (`test/plugins.test.mjs`): registry validation, `wiki-fs` lookups, `wiki-obsidian` lookups (all six capabilities), parser regression, bundle end-to-end with happy and error paths. Parser test group extended with `getDirectiveRegex` assertions.

### Changed
- `bundleAgentToString` now accepts an optional `registry: PluginRegistry` in `BundleOptions`. The CLI `bundle` command and the MCP `bundle` tool both construct it via `PluginRegistry.fromConfig(config)` and pass it through.
- `parser.ts` `DIRECTIVE_RE` extended to match `@wiki`. The unquoted-path alternative now uses a negative lookahead to avoid swallowing prop syntax — `@import` and `@tool` paths continue to parse identically.
- `PluginRegistry` constructor made private; callers must use `PluginRegistry.load()` or `PluginRegistry.fromConfig()` so validation is enforced.
- `src/commands/bundle.ts` reduced from ~315 lines to ~165 lines by extracting each directive branch into its own handler module.

### Notes
- No changes to `@import`, `@tool`, or `@memory` semantics.
- No auto-injection: using `@wiki` requires an explicit wiki plugin in `agent-pack.config.mjs`.
- The MCP `bundle` tool description now advertises `@wiki` alongside `@import`/`@tool`/`@memory`.
